forex_bolt_scalping — session summary (updated 2026-09-24)
===========================================================

WHAT WE BUILT
--------------
"forexbot" — a broker-agnostic, rule-based FX scalping bot. The trading brain
(strategy + risk) is fully separated from execution, so the SAME code runs in
backtest, paper, and live.

- Core: models.py (value objects), config.py (pydantic, YAML + .env),
  CLI in __main__.py with 6 commands: run, backtest, fetch-history,
  fetch-yf, check, report
- Broker layer (the only vendor code): Tickerall REST adapter to the
  Exness MT5 demo account, plus a WebSocket tick-stream mode with
  keep-alive, and a paper simulator
- Strategies (4 + ensemble): ma_cross and donchian_breakout (trend),
  rsi_reversion and bollinger_reversion (mean-reversion), combined by a
  weighted-vote ensemble (2 of 4 must agree to open/close)
- Risk manager: 0.5% equity-at-risk sizing, ATR x2 stop-loss, daily-loss
  halt, position caps — plus a trailing take-profit module (activate @25
  pts, trail 15, step 5) applied broker-side so the lock-in survives a
  restart. (Min-lot handling CHANGED this session — see below.)
- Infrastructure: live orchestrator engine, SQLite trade/equity store,
  cost-aware backtester, and a suite of debug scripts

CONFIGURATION LANDED ON
------------------------
- 10 pairs: EURUSDm, GBPUSDm, USDJPYm, AUDUSDm, USDCADm, USDCHFm,
  NZDUSDm, EURGBPm, EURJPYm, GBPJPYm
- Timeframe M15 — chosen as the best real-data config (compared M1/M5)
- Strategy: ensemble, min_votes 2, min_close_votes 2
- Risk: 0.5%/trade, ATR x2 stop, trailing TP on
- Backtest data: ~16,900 five-minute bars (60 days) and ~12,300 hourly

2026-09-24 — "THE BOT IS NOT PLACING ANY TRADES" INVESTIGATION
===========================================================================

BOTTOM LINE
-----------
The bot is NOT broken and NOT stuck. It is alive, receiving fresh bars, and
it DID trade (most recent open ~20 min before investigation). The real issue
is that it trades FAR LESS than the strategy generates signals for — most
attempts die downstream, and the ensemble is deliberately selective.

EVIDENCE (last ~13h, from the trade store: 17 open attempts)
------------------------------------------------------------
  outcome                         count    share
  open_failed (broker timeout)     10     ~60%   <-- BIGGEST killer
  open (filled)                     5     ~30%
  vetoed (sized below 0.01 min)     2     ~12%   both JPY / volatile bars

ROOT CAUSES, ranked by impact
-----------------------------
1. BROKER "trade reply timeout"  (~60% of attempts) — Exness-side reply
   timeouts via Tickerall. The adapter only retries errors flagged transient
   (broker/tickerall.py _call), and a timeout is treated as a FINAL failure
   and given up on — even though each order carries an idempotency_key, which
   makes a retry SAFE (broker de-dupes). A timeout is an unknown state, not a
   rejection; it is exactly the case that should retry.
   STATUS: FIXED — see "FIX APPLIED 2026-09-24 (timeout retry)" below.

2. MIN-LOT VETOES  (~12% of attempts, JPY/volatile) — at ~436 equity and
   0.5% risk the budget is ~2.2. Risk-based size = budget / (stop_distance x
   100000). That lands BELOW the 0.01 broker minimum on JPY pairs and wide-
   ATR bars, so those opens were skipped. NOTE: this is a MINOR blocker (only
   2 of 17) — the account is small, not the strategy.

3. ENSEMBLE SELECTIVITY  (by design, caps total opportunities) — replayed the
   exact member logic on M15 bars:
     - 81% of bars  -> ZERO member votes
     - 17% of bars  -> exactly ONE vote (ALWAYS rejected; needs 2)
     - ~0.9% of bars (≈1.2 signals/day per symbol) -> reach 2-of-4 consensus
   The "lone vote" bars are the biggest opportunity sink. This is the
   strategy working as intended, just low-frequency.

KEY FACT: SIZING IS NOT THE MAIN PROBLEM
----------------------------------------
For the primary USD-quoted pairs, 0.5% sizes to ~0.02-0.05 lots (well above
the 0.01 min) on calm bars; vetoes are rare and concentrated on JPY pairs /
volatile bars. So "fix the capital/sizing" has a SMALL effect on trade count.
The dominant lever is the broker timeout (now addressed — see below).

FIX APPLIED THIS SESSION (the "sizing/capital" item you chose)
--------------------------------------------------------------
A MIN-LOT FLOOR: when the risk-based size lands below the broker's 0.01
minimum, FILL AT THE MINIMUM LOT instead of skipping the trade. The extra risk
is bounded to the min lot's entry->stop distance and is flagged in the reason.
Standard small-account solution; fully reversible.

Files changed:
- config.py            RiskConfig.floor_to_min_lot: bool = True (new)
- risk/manager.py      below-min -> floor to min (approved+flagged) when the
                       flag is true; vetoes as before when false
- config/default.yaml  floor_to_min_lot: true (documented)

Verified (scripts/_verify_minlot_floor.py, real 436 equity):
  USDJPYm 40-pip stop (size ~0.0086, below min):
    floor=TRUE  -> APPROVED 0.010 lots  [flagged: risked more than target]
    floor=FALSE -> VETOED  (old behavior)
  EURUSDm 7-pip stop (size ~0.03, above min):
    floor=TRUE  -> APPROVED 0.030 lots  (unchanged)

FIX APPLIED 2026-09-24 (timeout retry — the "bigger lever")
------------------------------------------------------------
BROKER "TRADE REPLY TIMEOUT" IS NOW RETRIED, not given up on. Verified in the
trade store: all 10 open_failed rows were exactly
`[BROKER_REJECTED] trade reply timeout (msgId=...)` — Exness's matching
engine didn't answer in time, so the order state is UNKNOWN (may have filled),
yet the SDK classified it as a final rejection (transient=False) and _call
re-raised immediately.

The fix: in forexbot/broker/tickerall.py, _call now recognizes the
"trade reply timeout" message (regex, case/format tolerant) as a retryable
unknown state — bounded by the existing _max_retries (3) with a short flat
3s delay (the broker is UP and answering; latency, not connectivity). Safety
guard _trade_timeout_retryable: orders.place retries ONLY with an
idempotency key present (the broker de-dupes — the same key is reused across
all retries of one place() call, since kwargs are built once); close (by
ticket) and modify (absolute level) are repeat-safe; reads are side-effect
free. sessions.start is EXCLUDED (a repeat of a landed start leaves a double
session that doesn't self-heal). True rejections (e.g. INVALID_STOPS) still
fail fast, and transient retry behavior is unchanged.

Verified (scripts/_verify_timeout_retry.py, offline fake SDK client raising
the real tickerall exception classes): timeout-then-fill retries under the
SAME key and succeeds; timeout-every-time gives up after 4 attempts;
INVALID_STOPS not retried; ServiceUnavailable still retried; reads and
modify retry; sessions.start and keyless place() stay fail-fast. 10/10 pass.

JPY-CROSS P&L BUG — found in the first sweep, FIXED (backtest-only)
--------------------------------------------------------------------
The first H1 sweep showed "monster" results on exactly the 4 non-USD-based
JPY crosses (GBPJPY +819%, CADJPY +393%, AUDJPY +390%, NZDJPY +333%) while
the correctly-priced USDJPYm made only +39.6%. Root cause:
  1. broker/paper.py _account_pnl settled JPY P&L at PARITY for those pairs
     (1 JPY treated as 1 USD → ~150× overstated), and
  2. the backtester gave the risk manager no fx table, so JPY-cross SIZING
     was also at parity (positions landed at the 0.01 min-lot floor).
LIVE WAS AFFECTED NEITHER WAY: the orchestrator passes real fx rates and
Exness settles P&L in account currency.

A/B proof: scripts/_verify_jpy_cross_pnl.py (parity vs avg-USDJPY 152.5 —
trades/win-rate/PF identical, returns collapse to the normal league).

FIX (in code now):
- broker/paper.py      set_fx_rates(); _account_pnl uses it (parity is now
                       only the last resort, documented as ~150× wrong for JPY)
- backtest/runner.py   Backtester(fx_rates={…}) feeds BOTH risk sizing and
                       P&L conversion (currency code → account $ per unit)
- scripts/backtest_all_h1.py  auto-derives 1 JPY→USD from cached USDJPYm
                       data (override with --usdjpy N)
Corrected JPY crosses: GBPJPY +64.7% · CADJPY +43.0% · AUDJPY +40.5% ·
NZDJPY +33.7% — still top-tier, so the edge is REAL; the bug only inflated
it ~150×. Known remaining approximation: CHF crosses (GBPCHF/EURCHF) still
size/mark at parity (~±10%, the documented cross approximation).
